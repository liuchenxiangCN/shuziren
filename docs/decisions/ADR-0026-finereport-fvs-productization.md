# ADR-0026: 产品收敛为 FineReport / FVS 多大屏数字人平台

## Status

Accepted

顶层产品方向和 P0 参数已确认；官方插件契约作为 P2 外部门禁，内置数据库引擎、备份介质和 RPO / RTO 在 P1 冻结。本状态不表示目标能力已经实现。

## Date

2026-07-26

## Context

现有仓库已完成通用可配置数字人 POC、能力 Provider 抽象、客户配置覆盖、受控控屏、问数、知识库和运维基础。现有实现仍以启动时选择单个客户配置和全局服务实例为主，不能同时承载多块使用不同数字人、FVS、问数、知识库和语音配置的大屏。

新的产品目标明确限定为已经采购 FineReport、并使用 FVS 建设大屏的客户，同时要求:

- 一个客户部署内按单站点管理多块大屏，并保留未来多站点扩展层级。
- 目标架构为未来 2D / 3D Renderer 预留版本化热插拔接口，首批不承诺具体格式。
- Dora、知识库、LLM、ASR、TTS 和问数 Provider 均可按屏配置。
- 保留数据库和 Excel 问数，并新增帆软官方 FineReport 插件问数。
- 将当前监控页面升级为完整后台管理平台。
- 产品设计保持高可配置、实用、安全和可标准交付。

## Decision

1. 产品定位从“面向任意客户和任意大屏场景的通用 POC”收敛为“面向 FineReport / FVS 既有客户的本地化多大屏数字人管理平台”；产品适配目标为 FineReport / FVS 11.0 大版本及之后版本，生产支持以精确组合兼容矩阵为准。
2. 产品 V1 采用单客户物理隔离、多环境、单站点、多大屏的部署边界，不先建设跨客户共享数据的公有云多租户平台；领域模型保留 Site 层级。
3. 系统拆分为控制面与多大屏运行面。每块大屏通过设备身份解析自己的 RuntimeBinding 和不可变 ConfigRelease，不再依赖一个全局客户配置服务所有大屏。
4. Dora、LLM、问数、知识库、ASR、TTS、数字人渲染和 FVS 控制统一由 CapabilityProfile 和 Provider Adapter 编排，并保留 Mock Provider 作为开发、预览和故障演练能力。
5. FineReport 官方问数插件作为一等 Provider 设计，但在官方 API、认证、会话、权限继承和升级稳定性确认前只处于“待契约验证”状态；插件由客户安装到 FineReport 工程并负责合法授权，产品只交付连接器，不分发插件，核心代码不耦合插件内部路径。
6. V1 只冻结 AvatarRendererProvider / AvatarPackage、客户端预取、原子切换和回滚契约，不承诺具体 2D / 3D 格式；真实 Renderer Adapter 在获得合法资产和供应商资源后另行认证，普通资产包不得包含任意可执行脚本。
7. 当前 `/ops` 和 `/ops/config` 演进为带产品内置本地用户 / RBAC、资源管理、发布、监控、审计、备份和升级能力的后台控制面；V1 不接 AD / LDAP / OIDC。
8. 所有控屏继续使用 `action_id` 加后端白名单校验，禁止模型生成代码直接执行。
9. 现有 POC 作为功能和交付基线保留；本 ADR 不表示目标产品能力已经实现，也不在本轮修改运行时 API 或数据契约。
10. 产品不按许可证硬编码大屏数或并发会话数上限；首版保证至少三路并发的正确性和隔离，不承诺高并发吞吐、集群 SLA 或无限性能。
11. 控制面默认使用内置数据库，运行日志和会话明细默认保留 3 天且可配置；迁移到外置数据库后不设产品留存上限。内置引擎、备份介质和 RPO / RTO 在 P1 冻结。
12. 数据库问数首批覆盖 MySQL、Oracle 和 PostgreSQL，并继续强制专用只读账号、受控数据集、参数化查询、白名单、超时、最大行数和审计。
13. 后台用户身份、DeviceEnrollment 大屏设备身份和 ScreenInstance 绑定的 FineReport 展示 / 服务身份必须分离。

## Consequences

### Positive

- 产品价值与 FineReport / FVS 客户的既有资产和采购前提直接对齐。
- 多大屏、数字人、能力和 Provider 可以复用、组合、发布和回滚。
- 客户化从核心代码分叉转为可治理的解决方案配置。
- 官方插件、数据库和 Excel 可以通过统一问数契约共存。
- 后台从排障工具升级为实施、运营和运维的完整工作台。

### Trade-offs

- 现有全局 Settings、全局 Provider 和单客户 YAML 不能直接扩展为产品控制面，需要领域模型和运行时解析重构。
- 需要新增设备身份、RBAC、Secret Store、配置版本、发布、资产、兼容矩阵和产品级存储。
- 真实 2D / 3D 不进入首批格式承诺；未来每个 Renderer 仍需独立维护浏览器、显卡、格式和许可证兼容性。
- FineReport 官方插件的接口和授权依赖厂商确认，不能仅凭本地插件包静态信息承诺。
- 产品自建本地用户体系后，需要自行承担密码、会话、账号锁定 / 重置和审计安全责任。
- “无产品硬数量上限”不等于无限性能，交付容量仍受硬件、网络和外部 Provider 限制。
- 标准交付需要额外建设安装升级、备份恢复、容量、安全和支持证据。

## Follow-up

- 以 `docs/17_STANDARD_PRODUCT_DESIGN.md` 作为 P0 目标设计。
- 以 `docs/integrations/FINEREPORT_AI_PLUGIN_INTEGRATION.md` 管理官方插件证据和待确认契约。
- P0 产品边界已经冻结；P1 先冻结领域模型、三类身份、配置 / 发布、存储 / 留存和 Provider 数据契约，再进入控制面实现。
- 官方插件契约继续作为 P2 外部阻断项并行跟踪。
